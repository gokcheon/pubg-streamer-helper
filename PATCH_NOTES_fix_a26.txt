[1] 한 줄 요약
깃허브 자동 배포 파이프라인(버전 단일 진실·자동 업데이트·서버 빌드·올리기.bat) + 사용 설명서(메뉴얼.html) +
설명서 버튼·최초 실행 안내 카드·업데이트 배너를 넣었다. OCR 코드는 건드리지 않았다 (회귀 52/52 baseline 그대로 유효).

[2] 큰 그림 — 프로젝트의 현재 위치
- 이 앱은 곡천님 한 명이 아니라 모든 PUBG 스트리머에게 배포하는 도구다. 그래서 "설치하면 알아서 최신 버전이 되는" 구조가 먼저 필요했다.
- a25까지: 로컬에서 build_exe.bat → build_installer.bat 으로 exe 를 만들어 zip 으로 전달. 업데이트 알림 없음, 버전 상수 없음.
- a26: 보드게임 오버레이(board-overlay fix33)에서 검증된 방식을 그대로 이식. 곡천님이 올리기.bat 한 번 누르면 깃허브 윈도우 서버가
  PyInstaller + Inno Setup 으로 설치 exe 를 만들어 Releases 에 올리고, 설치판 앱이 시작할 때 그걸 보고 배너를 띄운다.
- 작업 순서(곡천님 확정): ① a26 깃허브 파이프라인 → ② 메뉴얼 → ③ UI 통일 시안 → ④ OCR 게이트·인원감지·상한. a27 = 치킨 보너스 미작동 + 카드 수정 전송.

[3] 이번 fix 의 핵심 결정과 이유

3-1. 버전 단일 진실 = version.py (APP_FIX=26, APP_LABEL="fix_a26", APP_VERSION="1.0.26")
   - 이유: 업데이트 비교·설치마법사 AppVersion·git 태그·화면 표시가 한 군데서 나와야 버전이 안 꼬인다.
   - 태그 이름은 기존 명명 규칙(fix_aNN)을 유지. updater.tag_fix() 는 태그의 마지막 숫자만 보므로 fix_a27 / fix27 / v1.0.27 전부 27 로 읽힌다.
   - build.yml 에 "version.py label == 태그" 검사를 넣었다. 다르면 빌드를 일부러 실패시킨다 (zip 폴더명만 올리고 version.py 를 안 고친 실수 방지).

3-2. 공개 저장소에 개인 정보가 올라가지 않게 — config.json 을 저장소에서 빼고 config.default.json 템플릿 도입
   - 문제: config.json 에 치지직 Client ID/Secret 이 저장된다. 올리기.bat 은 폴더 전체를 스냅샷으로 올리므로, 곡천님이 그 폴더에서 앱을 한 번이라도
     실행한 뒤 올리면 키가 공개될 수 있었다.
   - 결정: .gitignore 로 config.json / chat_tokens*.json / history.json / logs / screenshot / debug / overlay.txt / chat_outbox.txt 차단.
     저장소와 빌드에는 config.default.json(빈 템플릿)만 들어가고, bootstrap_runtime_files() 가 config.json 이 없으면 템플릿에서 만든다.
     load_config() 폴백 목록에도 config.default.json 추가. tests/regression/run_regression.py 도 config.json 없으면 템플릿으로 폴백.
   - 기각한 대안: 올리기.bat 에서 config.json 의 키 필드만 지우고 올리기 → 스크립트가 한 번 실패하면 그대로 올라가는 구조라 위험. 파일 자체를 막는 쪽 선택.

3-3. 업데이트 확인은 반드시 백그라운드 스레드
   - pywebview 의 js_api 메서드는 UI 스레드와 별개지만, requests 8초 대기 동안 poll_state 가 밀리면 창이 멈춘 것처럼 보인다.
   - check_update() 는 스레드만 띄우고 바로 반환, 결과는 poll_state()["update"] 로 400ms 폴링에 실려 간다. 다운로드 진행률도 같은 길(update_progress).
   - 앱 종료는 다운로드 스레드에서 _tray_quit_app() 호출 (트레이 스레드에서 이미 쓰던 경로라 thread-safe 검증됨).

3-4. 폴더판(소스 실행)에서는 자동 설치를 하지 않는다
   - 설치 exe 는 Program Files 설치판을 덮어쓰는 물건이라, python main.py 로 돌리는 곡천님 개발 폴더에서 실행하면 엉뚱한 곳에 설치된다.
   - updater.is_frozen() 이 False 면 [업데이트]는 릴리스 페이지만 연다.

3-5. 메뉴얼.html 은 단일 파일 + 스크린샷 내장(base64)
   - 보드게임 메뉴얼과 같은 구조(차례 / 섹션 카드 / 팁·경고 박스 / FAQ). 앱 리소스로 PyInstaller --add-data 에 포함되고, open_manual() 이
     RUNTIME_BASE_DIR → RESOURCE_BASE_DIR 순으로 찾아 os.startfile 로 연다.
   - 스크린샷은 pywebview API 를 스텁으로 바꿔 Chromium 에서 렌더링한 것 (실제 앱과 같은 index.html). UI 통일 작업 뒤에 갈아끼울 예정.

3-6. 최초 실행 안내 카드
   - config.manual_seen 이 false 면 메인 위에 반투명 카드. "설명서 열기" / "나중에 볼게요" 둘 다 manual_seen=true 로 저장.
   - 기존 사용자(a25 config.json 에 키 없음)도 a26 첫 실행 때 한 번 본다 — 의도한 동작.

[7] 잠재 함정 (다음 세션이 밟기 쉬운 것)
- 이 zip 에는 회귀 캡처 52장(68MB)이 빠져 있다 (전달 용량 제한 30MB). 올리기.bat 이 옆 폴더 fix_a25 의 captures 를 자동 복사한다.
  a25 폴더를 지웠다면 수동 복사 필요. 다음 버전부터도 zip 은 캡처 없이, 올리기.bat 이 직전 버전 폴더에서 복사하는 방식으로 갈 것 (bat 의 a25 경로를 직전 버전으로 갱신).
- 태그와 version.py 불일치 → build.yml 이 일부러 실패. zip 폴더명만 바꾸지 말고 APP_FIX 를 같이 올릴 것.
- 같은 태그 재푸시 불가. 빌드가 실패했으면 다음 번호로.
- Inno Setup 의 Korean.isl 은 6.5 부터 공식 내장. choco install innosetup 은 최신을 받으므로 OK. 로컬 빌드 시 구버전 Inno 면 한국어 줄에서 실패한다.
- .gitattributes 의 "* -text" 가 없으면 git 이 CRLF 를 LF 로 바꿔 .bat 이 깨진다 (보드게임 fix31 사고). 지우지 말 것.
- config.default.json 이 빌드에서 빠지면 설치판이 config 없이 떠서 시작 실패. build.yml 과 build_exe.bat 둘 다 --add-data 확인.
- updater 는 GitHub API 익명 호출(시간당 60회 제한). 시작 1회 + 수동 버튼이라 넉넉하지만, 폴링 루프에 넣으면 안 된다.
- 이 세션의 샌드박스는 GitHub API 가 403 이라 "연결 실패" 경로만 실제로 돌려봤다. 200 경로는 보드게임 앱에서 검증된 동일 코드이지만, 첫 릴리스 후 곡천님 컴에서 배너가 실제로 뜨는지 반드시 확인할 것.
- 사용안내.txt(구버전 텍스트)는 남겨뒀다. 내용이 메뉴얼.html 과 어긋나면 메뉴얼이 기준.

[8] 곡천님이 할 일 (사용 시나리오별)
A. 첫 배포

   2) 이 폴더의 올리기.bat 더블클릭 (로그인 창 뜨면 로그인)

   4) 그 exe 로 곡천님 컴에 설치 → 첫 실행 안내 카드 → 설정 탭 맨 아래 버전 fix_a26 확인, [업데이트 확인] 눌러 "최신 버전이에요" 확인
B. 빌드가 빨간 ❌ → Actions 로그 화면 캡처해서 다음 세션에 전달
C. 테스터에게 → Releases 링크만 전달. 다음 버전부터 앱이 알아서 알림.
