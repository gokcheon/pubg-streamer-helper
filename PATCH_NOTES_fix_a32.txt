PUBG 스트리머 헬퍼 1.0 fix_a32 — 패치 노트 (실험 일지 형식)
작성일: 2026-08-22
=====================================================================

[1] 한 줄 요약
창 드래그 회귀(a30~a31) 수정 2차. Windows 메시지(WM_NCLBUTTONDOWN) 방식을 버리고, 파이썬 스레드가 마우스 버튼이 눌린 동안
커서 위치를 읽어 SetWindowPos 로 창을 옮기는 방식으로 교체. a31 의 JS 진단 로그 제거. OCR 무변경, 회귀 52/52.

[2] 핵심 결정과 이유

2-1. 판정 근거 (2026-08-22 곡천님 실기)
   - a28~a31 을 전부 run_app.bat(폴더판)으로 띄워 비교 → a29 정상, a30 부터 창 고정. 즉 a30 의 easy_drag 끔 + begin_native_drag 교체가 원인.
   - a31 events.log 에 "[JS] [a31] titlebar mousedown → begin_native_drag 호출" 이 드래그마다 찍힘, errors.log 0바이트.
     → JS 핸들러·브리지·파이썬 호출까지는 전부 정상. Windows 가 WM_NCLBUTTONDOWN/HTCAPTION 을 받고도 창을 안 옮긴 것.
   - 가장 유력한 이유: ReleaseCapture() 는 "호출한 스레드가 가진 캡처" 만 푼다. a30 은 브리지를 막지 않으려고 별도 스레드에서 불렀으므로
     WebView2(UI 스레드)의 마우스 캡처는 그대로였고, 캡처가 남은 상태의 NC 드래그 요청은 무시됐다. (실기 확인은 아님 — 정황 추정)

2-2. 채택: 커서 추적 이동 (begin_native_drag 내부 교체, JS 쪽 호출은 그대로)
   - mousedown 1회 호출 → 스레드에서 GetCursorPos/GetWindowRect 로 오프셋 계산 → GetAsyncKeyState(VK_LBUTTON) 이 눌린 동안 6ms 간격으로
     GetCursorPos → SetWindowPos(NOSIZE|NOZORDER|NOACTIVATE). 캡처·메시지 경로·브리지 왕복 모두와 무관.
   - per_monitor DPI 에서 GetCursorPos 와 GetWindowRect 가 둘 다 물리 픽셀이므로 모니터 간 이동도 좌표계 일치.
   - 드래그 스레드 중복 방지(_drag_lock/_drag_thread). 드래그가 끝나면 events.log 에 "[a32] 창 이동: (x,y) → (x,y)" 1줄.
   - 기각: UI 스레드에서 ReleaseCapture+WM_NCLBUTTONDOWN 재시도(Invoke 경유) — 될 수도 있지만 또 한 번 추정에 기대는 셈. 확실한 경로를 택함.
   - 기각: easy_drag 복귀 — a29 의 느린 추적·브리지 정체 재발.

2-3. a31 의 JS 진단 로그 제거 (역할 끝).
