PUBG 스트리머 헬퍼 1.0 fix_a33 — 패치 노트 (실험 일지 형식)
작성일: 2026-11-18
=====================================================================

[1] 한 줄 요약
실행 시 "응답없음" 버그의 원인을 잡기 위한 진단 전용 버전. 시작 구간에서 프로그램이 멈추거나 강제 종료되면
모든 스레드의 코드 위치를 logs/startup_trace.log 에 남긴다. 앱 동작(OCR·전송·창·설정)은 바꾸지 않았다.

[2] 큰 그림 — 프로젝트의 현재 위치와 핵심 원칙
- 앱: PUBG 결과 화면을 OCR 로 읽어 치지직 채팅에 보내는 도구. 파이썬 백엔드(main.py 단일 파일) + pywebview(WebView2) 화면(ui/index.html).
- 현재 최대 문제(곡천님 지목, 2026-11-18): 앱을 실행하면 "응답없음" 이 뜨고, 안 뜰 때까지 껐다 켜기를 반복해야 쓸 수 있다.
  매우 오래된 버그이고 원인을 찾지 못했다. a29 의 "모니터 목록 빈칸·버튼 먹통·재시작하면 정상" 과 같은 뿌리일 가능성이 높다.
- 원칙: 한 번에 한 층. a33 = 진단 층만. 원인 줄이 기록되면 a34 에서 수정한다. 추정으로 고치지 않는다.
- 원칙: 파일 제작 전 설계안 승인. a33 승인 근거: 곡천님 발언 「확정」 (2026-11-18).

[3] 이번 fix 의 핵심 결정과 이유
3-1. 지금까지 확인된 사실 (a32 폴더판 logs/events.log, a31 폴더판 logs/events.log)
   - 2026-11-05 03:50:34 실행: "UI 로드 경로" 줄(창 만들기 직전)까지만 기록. 창 표시 기록 없음. 7초 뒤 재실행됨.
   - 2026-11-05 03:50:41 실행: 창 표시(둥근 모서리 줄)·업데이트 확인까지 기록. 그 뒤 "[JS] init OK" 없음, 종료 기록 없음.
   - 2026-08-22 04:20:09 (a31) 실행: 03:50:41 실행과 같은 모양.
   - 세 실행 모두 시작 1.2초 뒤 별도 스레드(StartupSteamWatchDelay)가 반드시 남기는 "스팀 자동 감지 중지: startup_delayed" 줄이 없다.
     → GUI 스레드만이 아니라 파이썬 스레드 전부가 멈춘 것으로 보인다 (프로그램 전체 멈춤).
   - 멈추는 구간: "webview.create_window ~ 화면(JS) 연결 완료" 사이. 폴더판(run_app.bat)에서도 발생.
   - 미확인: 위 실행들이 실제로 "응답없음" 이 떠서 끈 실행인지는 곡천님 확인 전(추정).
3-2. 추정 원인 (미확정)
   - pywebview 가 WebView2 를 초기화하는 순간 스레드끼리 서로를 기다리는 상태(교착).
     파이썬은 한 번에 한 스레드만 파이썬 코드를 실행하게 하는 잠금(GIL)이 있는데, GUI 스레드가 이 잠금을 쥔 채 다른 스레드의 일을 기다리고
     그 다른 스레드는 잠금을 기다리면 프로그램 전체가 멈춘다. 실행마다 순서가 미세하게 달라서 걸릴 때와 안 걸릴 때가 생긴다.
   - 지난 답변에서 냈던 "브라우저 임시 프로필 생성 지연" 추정은 '다른 스레드까지 멈춤' 을 설명하지 못해 후순위로 내렸다. 폐기는 아님.
3-3. 채택: faulthandler 타이머
   - faulthandler.dump_traceback_later 는 GIL 없이 도는 C 스레드라 프로그램 전체가 멈춘 상태에서도 기록한다.
   - 기각: 파이썬 감시 스레드 + SendMessageTimeout (처음 제안했던 1안) — 프로그램 전체가 멈추면 감시 스레드도 멈춰서 아무것도 못 남긴다.
   - 기각: 진단과 완화(private_mode 끄기 등)를 같이 넣기 — 증상이 사라지면 원인 확정 기회도 사라진다.
3-4. 강제 종료 감시(faulthandler.enable)는 시작 구간에만 켠다
   - 03:50:34 실행은 멈춤이 아니라 강제 종료였을 가능성도 있어 같이 잡는다.
   - 화면 연결이 끝나면 끈다. .NET 이 내부에서 처리하는 예외까지 기록될 수 있어 세션 내내 켜 두지 않는다.

[4] 만든 것
main.py
   - STARTUP_TRACE_LOG = logs/startup_trace.log
   - _startup_trace_begin(first_sec=8, second_sec=20): 파일 열기, faulthandler.enable, 8초 타이머.
     보조 스레드(StartupTraceFollowUp)가 8.5초에 "파이썬 스레드는 동작 중" 줄을 쓰고 20초 시점 타이머를 다시 건다.
   - _startup_trace_done(reason): 타이머 취소 + faulthandler.disable. log_debug 가 JS 의 "init OK" 문구를 받으면 호출. 창 닫힘·중복 실행 종료 경로에서도 호출.
   - _startup_trace_mark(text): 단계 표시 한 줄을 trace 파일과 events.log("[a33] +1.2s ...") 양쪽에 기록.
     단계: WebApi 초기화 완료 / create_window 반환 / webview.start 호출 / before_show / shown / loaded / 시작 구간 종료.
   - _log_runtime_versions: pywebview·pythonnet·clr_loader 버전과 WebView2 런타임 버전(레지스트리 pv 값)을 events.log 와 trace 파일에 기록.
   - window.events.loaded 에 기록 전용 핸들러 추가.
build_exe.bat, .github/workflows/build.yml
   - PyInstaller 옵션에 --copy-metadata pywebview --copy-metadata pythonnet 추가 (설치판에서도 버전을 읽을 수 있게).
   - 이 옵션이 없으면 설치판 로그에는 "pywebview=알 수 없음" 으로 찍힌다(동작에는 지장 없음).
버전·표기
   - version.py APP_FIX=33, installer.iss AppVer 1.0.33, 올리기.bat 회귀 캡처 복사 경로 a32→a31 순.
   - run_app.bat / build_exe.bat / package_dist.bat 의 화면 표기가 fix_a30 으로 남아 있던 것을 fix_a33 으로 고침.
변경 없는 것: ui/index.html, updater.py, OCR·전송·창 드래그 코드.

[5] 동작 범위
- 정상 실행(8초 안에 화면 연결 완료): startup_trace.log 에 머리줄 + 단계 표시 몇 줄만 남는다. 스레드 위치 기록은 없다.
- 8초 안에 연결이 안 되면: "Timeout (0:00:08)!" 아래에 스레드별 코드 위치(파일·줄 번호·함수)가 기록된다.
  · 그 뒤에 "(이 줄이 찍혔다 = 파이썬 스레드는 동작 중)" 줄이 있으면 → GUI 스레드만 멈춘 것. 20초 시점에 2차 기록이 이어진다.
  · 그 줄이 없으면 → 파이썬 스레드 전부 정지(프로그램 전체 멈춤). 2차 기록은 생기지 않는다(같은 내용이므로 불필요).
- 시작 구간에 강제 종료되면: "Windows fatal exception: ..." 또는 "Fatal Python error: ..." 아래에 위치가 기록된다.
- 느린 PC 에서 정상 실행이 8초를 넘으면 기록이 한 번 생긴다. 앱 동작에는 영향이 없고 "늦게 켜진 실행" 자료가 된다.
- 파일이 512KB 를 넘으면 다음 실행 때 새로 시작한다.
- 한계: 기록되는 것은 파이썬 코드 위치다. GUI 스레드가 .NET(WebView2) 내부에서 멈춰 있으면 "pywebview 의 어느 줄에서 .NET 을 호출한 상태인지" 까지만 보인다.
  그 경우에도 다른 스레드들의 위치와 조합하면 교착 상대를 좁힐 수 있다. 부족하면 a34 에서 .NET 쪽 덤프를 추가한다.
